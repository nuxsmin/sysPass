# sysPass use-case inventory for BDD

Status: maintained application use-case catalog. Source survey: 2026-11-16.

## Purpose and scope

This inventory is the maintained source of truth for the application's user-visible intents, their surveyed entry points, implementation evidence, and outstanding decisions. Use the stable IDs to plan BDD scenarios, implementations, and refactors. It covers the vault, access administration, authentication, configuration, installation, maintenance, and other product operations.

The project glossary's **Use Case** means a Domain class with one `execute()` entry point ([`CONTEXT.md`](../../CONTEXT.md), [`ADR-0003`](../adr/0003-use-case-and-command-result-convention.md)). This catalog also includes intents that bypass such a class. Section A retains one row per existing class for traceability, even where classes represent variants of the same intent. Section B records other intents and unresolved workflows. Group related rows into BDD features where appropriate, but preserve their IDs and boundary-specific examples.

This document catalogs what exists and what needs a decision. Explicit **Target** statements record product decisions for future BDD and refactors; they are not claims of current implementation. Other BDD focus cells are scenario prompts, not approved acceptance criteria. Resolve marked uncertainties against an issue, product decision, and applicable ADRs before asserting a desired outcome. Characterization tests may record existing behavior separately without endorsing a defect. The glossary remains authoritative for terminology and ADRs for architectural decisions; discrepancies with the code are explicitly flagged below.

When a change adds, removes, moves, or changes an intent or boundary, update its row, evidence, status, and scenario prompts in the same change. Preserve IDs for unchanged intents; cross-reference IDs when merging or splitting rows. Recheck the source snapshot when updating counts. An inventory entry is not evidence that a scenario has been implemented or passes.

Included: user-visible product behavior across Web/API/CLI, including operational flows. Excluded: static assets, resource delivery, selector/read-model plumbing, generic page composition, navigation-only and rendering-only behavior. The [UI interaction inventory](ui-interaction-inventory.md) owns JavaScript-to-backend wiring detail; it is not a substitute for this application-level inventory.

### Boundary and actor notation

- **W** — Web module; **API** — JSON-RPC API; **CLI** — console command; **Public W** — Web route reachable without normal login. A listed boundary identifies source-observed entry points, not proof that the full workflow succeeds.
- Actor labels, including those in section headings, are candidates for BDD setup, not a finalized authorization matrix: **Anonymous** (not signed in, including a person requesting or completing password recovery), **User** (authenticated sysPass user), **Admin** (application administrator or appropriately authorized profile), **API client** (user acting through an API Token), **Visitor** (Public Link holder), **Operator** (installer/maintainer using Web or CLI), and **System** (automated action). Actor exceptions are stated on individual rows or next to their tables.
- Section A identifies implemented Domain Use Case classes; section B identifies controller/service/other implementations. **Unresolved** identifies incomplete, conflicting, or unverified behavior and is not an implemented acceptance contract. Actual authorization must be verified at each boundary, including denied access.

### Public Link management — Admin/User; W

Public-link management classes are in `lib/SP/Domain/Account/UseCases/`. Public retrieval by hash is a separate service/controller flow listed in section B.

**Target:** an Account has at most one Public Link at a time; creating one requires current Account access, Public Link creation permission and Account password-view permission. An expired or exhausted link may be replaced by a newly created link under the same creation permissions; retire the old record only when replacement succeeds. Creation and refresh apply configured expiration time and maximum view count. Refresh requires the creator or a separately authorized administrator, current Account access, Public Link management permission and password-view permission; it generates a new URL and current Account snapshot, invalidates the old URL immediately and resets the view counter as one operation. A failed refresh leaves the previous link and view count unchanged. Link editing only changes notifications. The creator or a separately authorized administrator with Public Link management permission may delete a link even without current Account access. Existing links remain valid after access-control changes, including loss of creator access, until explicitly revoked, expired, exhausted or revoked by Account content changes. This intentional public-access behavior requires maintainer security review.

**Snapshot target:** expose Account name, login, password, URL, notes, Client and Category; do not expose custom fields, file attachments, history or access grants. Creating or refreshing a link for a linked child requires Account access and password-view permission for both child and parent.

### Notification — Admin manages; User receives/marks; W

Classes are in `lib/SP/Domain/Notification/UseCases/`. **Target:** Users may view and mark notifications addressed to them or explicitly broadcast to all Users; a broadcast is retained until an authorized administrator removes it, including for Users created after it was issued. Non-sticky visibility is subject to its visibility period and each recipient's dismissal state; sticky visibility follows the start and removal rules below. Cross-user viewing or marking, and access to admin-only notifications, require an appropriate explicit administrative permission, not merely a generic administrative role. Read state for a broadcast is per recipient; an administrator marking it for a recipient changes only that recipient's state. A sticky notification stays visible to its intended audience until an authorized administrator removes it, regardless of individual read state; sticky status does not override recipient or admin-only restrictions. The current model stores one `checked` flag, so per-recipient state is not established by that model. Confirm actor scoping at the driving adapter; a successful ID-based use case call alone does not establish that a User may access that notification.

**Notification validation and delivery targets:** Creation and editing require nonblank content after trimming and reject invalid time ranges before saving; validation failure leaves the existing notification unchanged. A successfully saved in-app notification remains available if optional email or push delivery fails; record the delivery failure separately without secrets. External delivery behavior and event ordering require source and implementation verification.

**Further notification targets:** A recipient may dismiss a non-sticky notification for themselves only; dismissal does not delete the notification or affect other recipients, including future broadcast recipients. Sticky notifications remain visible until an authorized administrator removes them. If a recipient loses eligibility and later regains it, preserve their previous read and dismissal state while denying visibility during ineligibility. Send optional email or push once at the notification's start time, or on creation if already active, to recipients eligible at delivery time; do not retry automatically. Future recipients of a broadcast see it in-app but receive no historical external delivery. Editing an undelivered notification updates its pending schedule, content and eligible audience; editing after delivery never schedules another send. Creation requires a recognized component and type; editing follows the legacy-value exception below. Both require an explicit valid audience: targeted, broadcast or admin-only. Sticky is independently selectable, subject to the existing explicit permissions and audience restrictions. Limit component and type to 100 characters each and content to 5,000 characters; reject over-limit input without truncation and preserve readability of existing notices. The current model has no schedule bounds and one shared checked flag; per-recipient dismissal and delivery scheduling are not established (`lib/SP/Domain/Notification/Models/Notification.php`; `lib/SP/Infrastructure/Notification/Repositories/Notification.php`).

**Taxonomy and channel targets:** Maintain a registry of stable, nonlocalized component and type identifiers with separately translated labels; registered Plugins may contribute identifiers. Preserve historical free-text values as readable legacy values without guessing their identity. On editing an existing notice, an administrator may preserve unrecognized legacy values unchanged, but changing either field requires a recognized identifier for that field. If a contributing Plugin is disabled, deleted or unavailable, existing notices retain its identifiers and last-known display labels; new notices cannot select those identifiers until the Plugin is registered and available again. An authorized notice creator explicitly selects no external channel, email, push or both. Deliver only through configured, available selected channels to eligible recipients with a usable email address or registered device; configured event mail must not duplicate the same notice delivery. If a selected channel is unavailable or an eligible recipient lacks the required address or device at delivery time, preserve the in-app notice and record a secret-free per-channel or per-recipient skipped or failed outcome without automatic retry. If the first delivery opportunity occurs after a non-sticky notification expires, skip the external send and record it as missed. If the scheduler resumes while a due notice remains active, attempt the pending send once at the next opportunity using current eligibility, without automatic retry. **Current gaps:** Web fields accept free text, and automatic Account notices can store translated labels (`app/modules/web/Forms/NotificationForm.php`; `lib/SP/Domain/Notification/Services/NotificationEvent.php`). Mail uses event subscriptions rather than a demonstrated per-notice channel selector (`lib/SP/Domain/Notification/Services/MailEvent.php`); push and scheduling are not established by the inspected paths. Historical values and Plugin extensions require persisted-data compatibility review.

**Registry and delivery concurrency targets:** Initially cover the observed Account request and Public Link view notification producers; add core identifiers as further producers are inventoried rather than assuming a complete set now. Prevent duplicate external send attempts when schedulers race or restart. An interrupted send with an uncertain outcome may be recorded as unknown and must not be automatically retried, even if that means delivery cannot be confirmed.

**Sticky start target:** A future-dated sticky notification becomes visible at its start time and remains visible until an authorized administrator removes it, regardless of its end time or individual read state. Audience and administrative access restrictions continue to apply.

### Security — Admin; W

Classes are in `lib/SP/Domain/Security/UseCases/`.

**Security retention and clear targets:** Retain ordinary event-log entries and Tracks until explicitly cleared; retain event-log-clear audit records indefinitely outside the ordinary clear set. Users with explicit security-audit permission may view and export these secret-free records, including actor, time and available client address; deny unauthorized access. Clearing an already-empty event log or Tracks collection succeeds as an audited no-op, subject to the same required audit persistence and failure rules. Clearing Tracks resets all active abuse controls represented by them; unlocking resets the affected Track's controls only. Current event-log and Track repositories return false for a clear affecting no rows; verify adapter behavior rather than treating that result as the target (`lib/SP/Infrastructure/Security/Repositories/Eventlog.php`; `lib/SP/Infrastructure/Security/Repositories/Track.php`). Security and retention changes require maintainer review.

**Abuse-control target:** Count failed login and API credential authentication attempts separately by client address and source in a rolling ten-minute window, including unknown or disabled Users and invalid API Tokens. Exclude authorization denials after successful authentication and requests rejected while already locked; successful attempts do not consume the failure budget. After ten failures reject further attempts for that address and source until the window expires or an authorized administrator unlocks or clears the relevant Track. This intentionally affects Users sharing an address. If tracking storage is unavailable, fail closed with a safe temporary-unavailable response and record a secret-free operator diagnostic when possible. The current Track service and repository require runtime verification: the repository query uses `LIMIT 1` while the service compares the returned row count to a threshold (`lib/SP/Domain/Security/Services/Track.php`; `lib/SP/Infrastructure/Security/Repositories/Track.php`). These authentication and abuse-control targets require maintainer security review.

**Track identity target:** A managed Track represents one client-address-and-source abuse-control bucket. Unlocking it resets the entire bucket's failure budget without affecting other buckets. Current persistence stores individual attempt rows and unlocks one row, not an established aggregate bucket (`lib/SP/Infrastructure/Security/Repositories/Track.php`). Migration and retention of existing Track data require compatibility review.

### User, User Group, and User Profile — Admin/User; W; User Group also API

Classes are in `lib/SP/Domain/User/UseCases/`. The User Group API exposes create, update, get, search, and single delete; Web exposes the inventory below. User/Profile management is Web-only in the surveyed API surface. Exceptions to the heading's actor label: `UC-USER-PASSWORD-RESET-REQUEST` and `UC-USER-PASSWORD-RESET` are Anonymous; W, without a normal authenticated-session prerequisite.

**Identity deletion targets:** Reject deletion of a User who owns live Accounts until ownership is explicitly resolved in a separate authorized operation, subject to existing Account privacy and transfer rules. A User cannot delete their own identity, including in a batch. Deletion, disablement or demotion must not leave the system without an enabled application administrator, including under concurrency. Block User Group deletion while it is a User's primary group or a live Account's main group; require separate authorized reassignment first. Block User Profile deletion while Users are assigned to it; require authorized reassignment first. Preserve deleted User and User Group identity in a non-login historical representation so Account history retains its original attribution without rewriting history. User, Group and Profile batch deletion rejects empty selections, processes duplicate IDs once and permits partial success with a safe result per distinct item. Each successful deletion and its required cleanup are atomic; failures do not prevent independent items from succeeding. These authorization-sensitive targets require maintainer security review; historical representation and persisted data require compatibility review.

**Identity deletion side effects:** Deleting an eligible User removes their direct Account grants, favorites, secondary Group memberships and User-targeted notifications, without removing broadcasts or other Users' targeted notifications. It atomically revokes their API Tokens and outstanding password-reset tokens and prevents existing Web sessions from continuing as that User. Public Links created by the User remain valid under their existing lifecycle rules and retain their creator attribution through the historical identity. After the creator is deleted, only a separately authorized administrator with Public Link management permission may edit or revoke the link; editing still requires current Account access. Deleting an eligible User Group removes its secondary memberships and Account sharing grants rather than transferring them. Deleting a User, Group or Profile detaches it from associated Item Presets: preserve a preset with remaining identity associations and delete it only if none remain. These effects are part of the respective atomic deletion; current schema cascades and restrictive references do not establish the complete target behavior.

**Identity and configuration targets:** A deleted User's historical identity is separate from active login identity. A newly created User may reuse the login without inheriting the deleted identity's historical attribution, permissions, notifications or credentials. A new User Group may reuse a deleted Group's name without inheriting its historical identity, Account access or memberships. If a deleted Account's deletion snapshot refers to a deleted User owner or Group main group, retain attribution without automatically granting access to a replacement; fail closed until a separately authorized recovery operation resolves the reference, without silently granting an administrator access to Account contents. Reference resolution requires history-restore permission and the relevant User or Group management authority; do not display Account content during reference selection. Block deletion of a User Group or User Profile while LDAP or SSO configuration names it as a default for newly created Users; require an authorized configuration change first. An administrator may disable or demote their own User if the concurrent last-enabled-application-administrator safeguard remains satisfied. Count administrators by their stored enabled and application-administrator status without requiring live authentication or external-service availability.

**Identity management authorization target:** Only application administrators may create, delete, enable, disable or change the application-administrator status of another application administrator. Non-application administrators cannot assign or change a User Profile, administrator flag or Group membership to give themselves or another User permissions beyond their own effective authority. This also applies when editing a Profile or Group would indirectly give an assigned or member User authority beyond the actor's. Define and verify effective-authority comparisons across indirect Profile and Group changes during implementation; maintainer security review is required. For partially successful identity batches, success audit events identify only deleted items; report failures safely per item without success events for failed deletions or sensitive credentials in logs.

**Delegation refinement:** For non-application administrators, compare newly granted authority, not the recipient's entire pre-existing authority, against the actor's effective authority. Include application actions and Account-level access acquired through Group membership, ownership or sharing, not Profile flags alone. Granting the Account-administrator flag additionally requires the actor to be an application administrator or already hold that flag. Only application administrators may make Profile or Group changes that alter an application administrator's effective authority. Non-application administrators cannot create or edit an unassigned Profile with application-action permissions beyond their own, grant an empty Group Account access beyond their own, or configure an LDAP or SSO default Profile or Group that would give newly provisioned Users authority beyond their own. These targets do not bypass Account privacy rules and require maintainer security review.

**Installer defaults target:** The installer-created Admin User Profile and Admins User Group are protected built-in identities and cannot be deleted. Appropriately authorized application administrators may rename and edit them, subject to the existing last-administrator and delegation safeguards. Current installer creation uses ordinary services with generated IDs, and the inspected deletion services do not establish this protection (`lib/SP/Domain/Install/Services/Installer.php`; `lib/SP/Domain/User/Services/UserGroup.php`; `lib/SP/Domain/User/Services/UserProfile.php`).

**Identity edge-case targets:** Process distinct batch User IDs in submitted order; when multiple enabled application administrators are selected, delete eligible Users only while the last-enabled-administrator invariant remains satisfied and report blocked items individually. Authorized Account-history and Public Link management views show a deleted identity's name at deletion, a deleted marker and a stable distinguishing identifier, without expanding existing view permissions. If an installation already has no enabled application administrator, allow authorized repair operations to restore one without blocking unrelated identity changes solely because of that pre-existing condition.

Check the delegation ceiling against the acting User's current authority whenever an operation grants new access; do not automatically revoke existing grants merely because their original delegator later loses authority. For non-application administrators, include currently ineffective Group memberships and sharing grants that could later grant access beyond the actor's authority if privacy or ownership changes. Reject a membership change that would grant a recipient access to an Account the actor cannot access, without identifying or disclosing that Account. Reference resolution for a deleted Account requires active replacement Users and Groups rather than historical identities; enforce the existing combined private/group-private compatibility rule before restoration. These targets require maintainer security review.

Apply the same delegation ceiling to each newly granted application action and Account access when non-application administrators import or map external Users and Groups, including access inherited through existing Groups. Reject an item that exceeds the ceiling with a safe result while allowing independent eligible items to succeed, without exposing inaccessible Account details. If both a deleted Account's recorded owner and main Group require replacement, resolve both references and restore the Account atomically without saving a partially resolved intermediate state. Block a Profile or Group edit that would leave the sole enabled application administrator without effective permissions to manage Users, User Groups and User Profiles, even if that User remains enabled and retains the administrator flag. Evaluate effective application actions, not live login or external-service availability.

**Shared preset and configuration implementation gaps:** An Item Preset may reference multiple User, Group or Profile associations and apply to multiple Users, but the current schema cascades deletion of the whole preset when any referenced identity is deleted (`schemas/dbstructure.sql`; `lib/SP/Infrastructure/ItemPreset/Repositories/ItemPreset.php`). The inspected Group and Profile deletion services do not check LDAP or SSO default references. Neither behavior establishes the targets above.

**Current deletion gaps:** The traced Web User delete endpoint does not invoke the form's self-deletion check; last-administrator protection was not found in the traced deletion or update paths. Current schema constraints block various live and historical references and do not establish the target policy. The traced batch services compare affected counts after deletion, without an enclosing transaction established; missing or duplicate IDs can lead to an error after matching rows were deleted. Cleanup and success events follow the count check. Verify deployed schema and runtime behavior rather than assuming these targets are implemented.

### Authentication, sessions, API Tokens, and public access

**Credential lifecycle targets:** A successful authenticated User password change keeps the session that performs the change, including its Master Key; it invalidates the User's other active Web sessions and all their API Tokens. A successful anonymous password reset invalidates all active Web sessions and API Tokens. Disabling a User immediately terminates active Web sessions, clears the session-held Master Key, prevents API Token use and invalidates outstanding password-reset tokens; a disabled User cannot complete a reset. Deleting a User revokes API Tokens and reset tokens and prevents existing sessions continuing as that User, per the identity deletion target. An invalidated session loses its Master Key; resuming vault access requires fresh authentication and Master Password unlock. If reset-mail delivery fails, prior unused tokens remain invalidated, the undelivered token is invalidated, the public response remains generic and an authorized operator receives the approved secret-free record. **Current gaps:** Web sessions retain session User/Profile state rather than rechecking disablement on each request; API requests check disabled status. Password change/reset and disable paths do not establish cross-session or token invalidation. These authentication, session and key-handling targets require maintainer security review.

### Account vault, access, history, credentials, and files

Core Account create/edit/delete/search/view APIs and Web controllers remain service-driven; `lib/SP/Domain/Account/UseCases/` currently contains only Public Link use cases.

**Account authorization target:** Every Web and API operation on an Account requires both the relevant User Profile action permission and the appropriate Account-level access. Account edit, password change, and deletion require edit access, not visibility alone. A private Account is accessible only to its owner, including against administrators and other explicit or group grants. A group-private Account is accessible only to Users whose primary group is the Account's main group, without administrator or secondary-membership override; if both privacy flags apply, both restrictions must hold. Subject to privacy and profile permissions, the owner and main-group members retain edit access ahead of conflicting direct read-only grants. Otherwise an explicit User grant takes precedence over secondary-group grants; if there is no direct User grant, any matching secondary-group edit grant permits editing. Retain the full-group-access configuration for evaluating secondary memberships in explicitly shared secondary groups; membership in the Account's main group remains recognized, subject to privacy. Global search requires both global configuration and profile permission and may reveal only name, Client and Category for otherwise inaccessible non-private Accounts, without login, URL, notes, custom fields, password, file names or history; discovery does not confer Account access. Enforce these rules server-side, including alternate entry points; current page, search, and mutation paths do not consistently use the same resource checks. These targets require maintainer security review before behavior changes merge.

**Account create and update target:** Web and API both require an Account name, an existing Client and Category, and a password unless an accessible parent Account supplies it. A linked Account may point only to an existing, accessible non-linked parent; reject self-links, chains and cycles. When a creator lacks permission-management authority, use that User as owner and their primary group as the Account's main group, ignoring attempted ownership or sharing overrides. Across Web and API updates, omitted optional fields and ACL collections remain unchanged; an explicitly supplied empty collection clears it. Fixed Item Presets still apply to controlled fields even when omitted, and win over conflicting explicit values or empty collections; the response reflects the effective saved value. Only the owner may set or clear privacy flags. Ownership transfer and User/group grant changes require permission-management authority and may be performed by the owner or a separately authorized Account administrator who already has Account access; edit access alone is insufficient to change grants. A User whose primary group is the current main group and who has permission-management authority and Account access may also change the Account's main group. On private Account ownership transfer, the former owner immediately loses access and the new owner gains access subject to their profile permissions. Reject transfer of an Account that is both private and group-private to a User whose primary group differs from the Account's main group unless the group-private restriction is also resolved. Additional field-specific validation remains to be decided. Current collection and adapter semantics differ, so do not assume the target is implemented.

**Linked credential target:** A User linking a child requires access and password-view permission for the parent. Revealing an inherited child password requires Account access and password-view permission for both the child and parent. Changing the child's parent requires access and password-view permission for both the current and new parents. Unlinking requires Account edit and password-change permission on the child and access and password-view permission for the current parent. Linking, unlinking or changing the parent atomically revokes the child's Public Link. A parent password change automatically changes its children's effective password and atomically revokes affected children's Public Links. If the parent is missing or inaccessible, password reveal and Public Link creation/refresh fail closed without a password fallback. An already issued child Public Link remains usable after its creator loses parent access alone, subject to the Public Link lifecycle above. Account names are trimmed and must contain at least one non-whitespace character on Web and API.

**Account validation and update atomicity target:** Duplicate trimmed Account names are permitted, including within the same Client and Category. An explicitly blank optional text field clears it; omission preserves it. Account passwords follow the configured Account password Item Preset or policy. Account creation, initial custom fields, grants and fixed preset effects are all-or-nothing on Web and API. For each updated Account, the update, history snapshot, custom-field changes and any required Public Link revocation succeed or fail together without partial state. An update with no effective change after presets succeeds without creating history or revoking a Public Link. Bulk edits apply the same single-Account rules but allow partial success; report individual failures. The current bulk writer uses a transaction, so do not assume partial success is implemented.

**Account field-length target:** Web and API enforce maximum lengths of 100 characters for name, 50 for login, 255 for URL/IP and 5,000 for notes, rejecting over-limit input rather than truncating it. URL/IP is optional text, not restricted to URL or IP syntax. Existing stored values remain readable and are not silently truncated during unrelated updates. These limits appear in the Web form; equivalent server-side enforcement across boundaries is not established.

**Account file target:** Each operation requires its profile action and Account access: view access for list, search, preview and download, and edit access for upload and deletion. Uploads enforce the configured size limit in KiB (1,024 bytes) against actual received bytes and reject upload errors and empty files. Preserve existing numeric settings when changing units, so their effective byte limits increase. The server-detected MIME allowlist is the authoritative type restriction; no separate extension allowlist or match against the client-declared MIME type is required. Application-layer encryption of file contents and thumbnails is not required by this target. Batch deletion deduplicates IDs and deletes all or none if a file is missing or unauthorized, without disclosing inaccessible file details. **Current gap:** the upload path uses 1,000 bytes per configured unit, accepts either declared or detected MIME and stores file bytes without application-layer encryption; end-to-end authorization is not established by the controller alone.

**Account history access and deletion target:** History operations require the relevant history action and applicable Account access and privacy restrictions. For an existing Account, apply its current access and privacy rules rather than the snapshot's recorded owner and privacy flags. For viewing or deleting a deleted Account's history, use the deletion snapshot's recorded ownership, main group and privacy restrictions for all its history. If that snapshot is missing, corrupt or ambiguously attributed, fail closed rather than falling back to older snapshots or administrator access until an authorized recovery process resolves the ambiguity. Historical password reveal also requires password-view permission. Explicitly authorized Users may delete history, including recovery snapshots; batch deletion is all-or-nothing. Warn when deletion removes the last usable recovery snapshot. When bulk edit requests a history purge, each Account's purge and edit succeed or fail together; an effective edit still creates its required pre-update snapshot. If the edit has no effective change after presets, the authorized purge still occurs without a new snapshot. **Current gap:** bulk Account edit can purge history before its update transaction, so a later failure can leave the purge applied.

For a deleted Account, reject deletion of its deletion snapshot unless all remaining history for that Account is selected and deleted in the same authorized, atomic operation. This avoids leaving history inaccessible solely because its authorization snapshot was removed.

**Account deletion and restoration target:** Single and bulk deletion create a recoverable deletion snapshot containing encrypted core fields and custom-field values for each Account. Deletion is rejected while linked child Accounts remain; they must first be reassigned or unlinked, and unlinking requires an independently encrypted password for the child. A successful deletion atomically revokes and removes its Public Link and stored snapshot, and removes Account files, favorites, Tag associations, sharing grants and live custom-field data while leaving shared Tag definitions intact. Snapshot or cleanup failure rolls back the entire deletion. A bulk deletion is all-or-nothing if any selected Account is missing, unauthorized or cannot be deleted. Restoring a deleted Account normally preserves its original ID and retained history and restores its encrypted core fields, custom fields, recorded owner, main group and privacy flags, but does not restore files, favorites, secondary sharing grants, Tag associations or Public Links. If the original ID is occupied, restore under a new ID and re-associate only the deleted Account's verified history, without moving or exposing the occupying Account's history; if attribution cannot be verified, fail closed without modifying data. Reject restoration if the recorded owner, main group, Client or Category no longer exists until an authorized User explicitly resolves those references. Restoration requires separately authorized history-restore permission and the deleted Account's privacy and ownership restrictions. Restoring a still-existing Account requires Account edit access, history-restore permission and a history entry belonging to that Account. First snapshot its current state, then restore historical core and custom-field values, including the historical password subject to password-change permission, while retaining its current owner, main group, privacy flags, sharing grants, files, favorites and Tags. An effective content change through restoration revokes and removes an existing Public Link, per `APP-LINK-VIEW`. Apply the same deletion cleanup semantics across Web, API and bulk paths. Current single and bulk paths differ in snapshot behavior, cleanup differs by boundary, and removed restoration currently inserts a new ID; do not assume the target is implemented. Persisted-data and ciphertext changes require compatibility review under ADR-0005.

### Category and Client

Both contexts provide CRUD/search through Web and API. Current implementation is service/controller-based: `lib/SP/Domain/Category/Services/Category.php`, `lib/SP/Domain/Client/Services/Client.php`, and their Web/API controller directories.

**Target:** Categories are flat, without parent/child relationships. A Category referenced by an Account cannot be deleted until its Accounts are reassigned. Account history references also block deletion; they must not be changed automatically, although an authorized user may explicitly delete the history first. A batch containing any blocked Category is rejected in full. The current model and schema are flat; verify deletion behavior at the relevant boundaries.

**Client deletion target:** Reject deletion while an Account or Account history entry references the Client; Accounts must first be reassigned and an authorized User may explicitly delete referencing history. ### Configuration, import/export, backup, and cryptographic administration

The Web configuration controllers use `ConfigFileService`, configuration services, and domain services directly. These operations are security-sensitive; follow [`security.md`](security.md) and obtain maintainer security review before turning them into behavior changes.

**Configuration targets:** Reject invalid submitted values rather than silently discarding them; preserve omitted or masked secrets. A failed save leaves the previous effective configuration intact, and a success audit follows persistence and required side effects. LDAP and mail checks use submitted settings without saving them and report actionable, secret-free failures, including timeouts. **Current gaps:** configuration XML is saved before its cache and subsequent callbacks; invalid mail recipients and event names can be discarded (`lib/SP/Domain/Config/Services/ConfigFile.php`; `lib/SP/Domain/Config/Dtos/ConfigInput.php`). Full rollback and boundary security require verification.

**Import targets:** Support seven-field CSV (Account name, Client, Category, URL, login, password, notes), KeePass XML and sysPass XML; do not claim support for binary KeePass or other MIME types merely listed in the code. Reject malformed files, failed integrity checks and invalid required decryption credentials before any changes. Otherwise allow independent per-record partial success with safe results and atomic creation per record. LDAP import creates missing Users and optionally Groups, skips existing identities without overwriting them, and reports safe per-item outcomes while continuing independent items, subject to the existing delegation ceiling. **Current gaps:** file importers catch some per-record errors within an enclosing transaction; sysPass XML integrity failure is logged but does not abort. The LDAP import path creates Users and Groups but does not establish membership mapping or comprehensive result reporting (`lib/SP/Domain/Import/Services/ImportStrategy.php`; `lib/SP/Domain/Import/Services/SyspassImport.php`; `lib/SP/Domain/Import/Services/LdapImport.php`). Import formats, authorization and persisted-data compatibility require review.

**Backup, export and recovery targets:** Full system recovery remains an operator-managed procedure, not an in-app restore; document required database, application files, configuration and keys, and version compatibility. Preserve previous usable backup and export artifacts until replacements are successfully generated and verified; clean up failed new artifacts where possible and emit no success event on failure. XML export is a privileged system-wide operation, including Accounts outside the actor's ordinary Account ACL, requiring explicit export permission and a nonempty export password. Treat backups and configuration artifacts as sensitive and access-controlled even when not encrypted by the application. **Current gaps:** the backup and export paths remove prior artifacts before completion; Web and API XML exports differ in verification and archiving, and the API returns a server path. No production whole-system restore action was established (`lib/SP/Domain/Export/Services/BackupFile.php`; `lib/SP/Domain/Export/Services/XmlExport.php`; `app/modules/api/Controllers/Config/ExportController.php`). Credential export and expanded access require maintainer security review; artifact and restoration compatibility require review.

**Master Password targets:** A change succeeds only when every required Account, history and Custom Field update and associated metadata are consistent; failure must preserve recoverability and must not silently accept skipped records. A Temporary Master Password remains a separate, time-limited means of updating Users' access to the existing Master Key, not a system Master Password rotation. **Current gaps:** per-record errors can be caught or records skipped during rotation, and configuration updates occur outside the data transaction (`lib/SP/Domain/Crypt/Services/MasterPass.php`; `lib/SP/Domain/Account/Services/AccountMasterPassword.php`). Key handling and persisted ciphertext require maintainer security and compatibility review.

**Import refinements:** Each valid imported Account creates a new Account even if its name matches an existing one; reuse matching Client, Category and Tag definitions and never overwrite existing Accounts. LDAP-imported Groups do not automatically change User memberships; mapping is a separate authorized operation.

**Artifact refinements:** Web and API XML exports verify the encrypted XML and publish a downloadable archive; API returns a protected artifact reference rather than a server filesystem path. A successful backup or export replaces the preceding set after verification, with no automatic retention of older sets beyond the previous set during replacement; operators manage longer retention. Backup verification checks both database and application artifacts for completeness and readability; full restore tests are a separate operator responsibility and should be documented. `sp:backup`'s custom path controls output, temporary artifacts and cleanup, without deleting artifacts in another directory. Configuration download produces a current, complete, explicitly authorized recovery snapshot containing secrets, warns that it is sensitive and fails clearly if it cannot be generated. The current snapshot path reads a stored database snapshot; its production refresh lifecycle was not established (`lib/SP/Domain/Config/Services/ConfigBackup.php`). The CLI destination needs runtime verification because its supplied path is not visibly rebound to the injected output handlers (`app/modules/cli/Commands/BackupCommand.php`; `lib/SP/Core/Definitions/CoreDefinitions.php`).

**Temporary Master Password refinements:** Default to one hour and allow an administrator-selected lifetime from one minute through 24 hours, expiring at the deadline. One active credential may be reused by eligible Users until expiry; replacement immediately invalidates its predecessor and 50 failed attempts expire it. For optional delivery, the administrator explicitly selects a recipient Group or all Users. Mail failure leaves the generated credential usable and reports a safe delivery failure without logging the credential. Hash-only update and hash refresh remain explicitly confirmed, authorized recovery operations; they do not re-encrypt Account data and must warn that incompatible credentials can prevent access. The inspected temporary credential creation precedes optional delivery, and current lifetime defaults differ between the Web action and service (`app/modules/web/Controllers/ConfigEncryption/SaveTempController.php`; `lib/SP/Domain/Crypt/Services/TemporaryMasterPass.php`). Review the recipient trust boundary and key lifecycle with a maintainer.

**Further operational targets:** A valid Temporary Master Password alone is insufficient: an enabled, normally authenticated User may use it only to update their own Master Key access; mail recipient selection is not an authorization grant. Optional mail is attempted once for selected eligible Users with usable addresses, with safe per-recipient failures and no automatic retry; never log the credential or show it in ordinary later views. Enforce expiry, replacement and the 50-failure limit atomically under concurrency so a racing request cannot use an invalidated credential. After successful system Master Password change, invalidate existing Web sessions and API Token vault access; require fresh authentication and appropriate key unlock or token refresh. Hash-only recovery requires maintenance mode and a valid currently unlocked Master Key; failed validation or metadata persistence leaves existing data untouched. These key and session targets require maintainer security review and persisted-data compatibility tests.

Reusing imported Client, Category and Tag definitions follows their normal normalized-name and uniqueness rules; reject ambiguous matches instead of choosing arbitrarily. Export artifact download rechecks authorization and permits only the authorized requester or separately authorized administrators; its reference exposes neither a bearer secret nor a server path. Document periodic complete restore exercises in an isolated environment, checking application access and representative encrypted data, separately from per-backup verification.

Show a newly generated Temporary Master Password once to the authorized administrator at creation, including when optional email fails; ordinary later views cannot retrieve it. The latest protected export remains available until replacement or explicit authorized deletion, without automatic expiry. Disabling LDAP, mail or proxy retains saved settings and credentials for later re-enablement; an authorized actor can explicitly clear credentials. Saving enabled LDAP or mail settings validates structure but does not require the external service to be reachable; the separate check reports connectivity failures. Enabled generic wiki configuration requires valid HTTP or HTTPS destinations and a nonempty filter; encode Account names in URLs and show links only for Accounts already visible to the User. Retired DokuWiki API and embedded views remain unsupported.

Master Password rotation requires maintenance mode and a verified recoverable backup before starting. On failure keep the system in maintenance and provide safe recovery instructions; do not claim complete rollback without evidence.

For rotation, as for upgrade, the operator explicitly attests that a recent backup succeeded and was verified; an external backup is acceptable. Explicit export-artifact deletion requires the same requester-or-authorized-administrator check as download, removes the server-side artifact and reports failure if cleanup cannot be completed.

CSV import requires UTF-8, accepts an optional UTF-8 byte-order mark and an explicitly selected single-character delimiter, and rejects invalid encoding or malformed rows before any changes. Import results identify each input by a safe line or item position and report created, skipped or failed with a non-secret reason; do not echo passwords or inaccessible Account data.

**Explicit Session 5 deferrals:** Defer the exact supported sysPass and KeePass XML version matrix until compatibility fixtures and current behavior are inventoried. Defer generic wiki filter syntax and matching semantics until source characterization. Defer field-specific configuration bounds, supported upgrade source versions and detailed reinstallation safeguards pending source and compatibility investigation. Defer exact backup completeness checks and step-by-step recovery procedures until representative artifacts can be tested in an isolated environment. These deferrals do not approve legacy behavior or waive the backup, authorization and recovery targets above.

### Installation, upgrade, system status, and CLI

**Installation and operations targets:** A fresh installation does not require a force flag. Reinstallation of an installed instance is rejected by default and requires explicit force and confirmation; keep secrets out of logs. All three CLI commands return nonzero on failure or lock contention and zero only on successful completion, with secret-free diagnostics. An upgrade requires confirmation, valid upgrade authorization, exclusive execution and a verified pre-upgrade backup; failure reports completed steps and recovery instructions without claiming atomic rollback. ADR-0005 requires a pre-upgrade database backup for rollback after durable payload migration. **Current gaps:** the CLI installer currently requires force even on a fresh installation; Master Password CLI lock contention returns success. Upgrade durable payload migration commits per row and schema statements are not established as one transaction (`app/modules/cli/Commands/InstallCommand.php`; `app/modules/cli/Commands/Crypt/UpdateMasterPasswordCommand.php`; `lib/SP/Domain/Upgrade/Services/UpgradeDurablePayloads.php`; `lib/SP/Domain/Upgrade/Services/UpgradeDatabase.php`). Backup verification and recovery procedures remain to be defined and tested.

**Upgrade backup attestation:** The operator explicitly attests that a recent backup has succeeded and been verified; the backup may be external and need not be created or located by sysPass. The applicable recovery instructions must still account for ADR-0005's pre-upgrade database backup requirement.

**Installation failure target:** Report completed steps and safe recovery instructions; do not mark the instance installed until initialization succeeds and do not silently delete pre-existing database or configuration data. Installation is not claimed to be fully rollback-atomic. **Current source gap:** Failure cleanup invokes database rollback; in hosting mode it drops sysPass-named tables, and otherwise can drop the database and user. Whether pre-existing data can be affected under particular installation conditions requires runtime verification (`lib/SP/Domain/Install/Services/MysqlSetup.php`; `lib/SP/Domain/Install/Services/Installer.php`). Reinstallation safeguards remain deferred below; security and persisted-data compatibility review are required.

### Current test tiers to use when implementing scenarios

- Domain Use Case behavior: Unit Tests with in-memory port fakes.
- Repository behavior affecting SQL/hydration: DB-backed Tests against MariaDB.
- Web routes, authorization and rendered/translated response: HTTP Integration Tests, including denied-access cases.
- JSON-RPC and console contract: API and CLI Adapter Integration Tests.
- Browser tests remain limited to UI Smoke and UI Workflow wiring contracts; they are not a substitute for backend authorization or full BDD workflows.

### Gaps to resolve during BDD refinement

1. **Account is the largest service-driven area.** Account create/edit/delete/view/search, password operations, history, files, favorites, access requests, and bulk management are not represented by Account Domain Use Cases. The Account UseCases directory covers Public Links only.
2. **Category and Client are service/controller-driven.** Their CRUD/search APIs are not use-case-backed.
3. **Authentication and session lifecycle are service/controller-driven.** Make local, LDAP and browser/Basic login, Master Key unlock, failed login, session expiry, and logout explicit scenarios. Password-reset request and completion are public Web flows, not authenticated-only actions.
4. **Configuration, installation, upgrade, import/export, backup, and cryptographic administration are service/controller/CLI flows.** Their validation and side-effects are split across layers.
5. **API parity is incomplete.** API covers 29 methods in six areas; it does not expose all Web behavior. Do not imply parity by copying Web scenarios wholesale.
6. **Authorization often sits outside the Domain Use Case.** A Use Case unit scenario cannot by itself prove Web/API authorization; assert denial at the relevant adapter boundary.
7. **Public-link management and public-link viewing are different intents.** `GetPublicLinkUseCase` is ID-based management; anonymous retrieval by hash, expiry, max-view enforcement, and serialized payload behavior are in `ViewLinkController`/`PublicLinkService`.
8. **Some outcomes are undefined or source-level defects.** The UI interaction inventory records route/outcome discrepancies, including handlers that continue after error envelopes; its `status/checkRelease` missing-route observation is stale against the current controller and dispatch source. Public Link editing has a target contract but no save route. DokuWiki API configuration/testing and embedded DokuWiki viewing are retired; their missing routes are not implementation requirements.
9. **No dedicated reporting subsystem was found.** Event log, Tracks, and Account history are the product's nearest audit/history surfaces; do not invent separate report use cases without new evidence.
10. **Security-sensitive behavior requires maintainer review.** The decided authentication, Public Link and notification authorization targets, along with other changes to authorization, cryptography, Master Password and credential export/import, need explicit maintainer security review before behavior changes merge; see [`security.md`](security.md). A target decision is not itself that review.
11. **Category deletion target requires verification.** Categories are flat; Account or Account history references block deletion, and a batch with a blocked, missing, or unauthorized Category is rejected in full. Preserve historical information unless an authorized user explicitly deletes the history. Verify current behavior and cover both boundaries without assuming the batch implementation is atomic.
12. **Password-reset behavior differs from the target and ADR-0003.** `RequestPasswordResetUseCase` emits the request event before sending mail; `ResetPasswordUseCase` marks the token used before the password update. The targets specify success-event timing, separate failure recording, a generic response, token invalidation on a new request and retryable atomic completion. Verify transaction and failure behavior rather than assuming it. The failure-recording mechanism must respect ADR-0003 and avoid exposing secrets.
13. **Identity deletion and delegation need implementation.** The targets above decide ownership and membership blockers, historical identities, self-deletion, last-administrator protection, partial-success batches, delegation limits, installer defaults and deleted-Account reference recovery. Current schema constraints and services do not establish those targets. Security and persisted-data compatibility review remain required.
14. **Credential lifecycle policies need implementation.** Targets now require 90-day default per-token expiry with a finite maximum, scoped rotation and redaction; password-change/reset session and token invalidation; immediate disablement effects; and fresh authentication before Master Key reload. Verify them against API/session paths and retain security review. Provider registration order and configuration-dependent authority still require implementation characterization against the approved no-fallback rule.
15. **Operational detail remains unresolved.** Configuration field-specific bounds and wiki filter semantics; import XML versions and remaining collision handling; exact backup completeness checks, recovery instructions and upgrade supported versions; and installation/reinstallation safeguards require further decisions or source verification. Temporary credential delivery eligibility, secure one-time presentation and the mechanisms for atomic rotation, artifact authorization and key recovery need implementation design and security review. The approved targets above do not establish current behavior or complete cross-boundary coverage.
16. **Identity authorization needs characterization.** Deleted-identity recovery authorization and the horizon for future delegated access need precise implementation characterization without weakening the approved fail-closed and delegation rules.
17. **Public and partially initialized routes need a boundary audit.** `app/modules/web/Init.php` lists installation, upgrade, status, bootstrap environment, resource and error controllers for partial initialization; those controllers skip the full initialization branch, including its CSRF check. This list alone does not establish anonymous access or successful runtime reachability. The two legacy status paths' inspected dispatch and controller code have no explicit authentication or ACL gate, unlike `status/checkRelease`; runtime and external proxy restrictions remain unverified. Verify the other routes and denied requests before assigning actors. Resource and error presentation and bootstrap environment are supporting behavior rather than separate intents under this inventory's scope. `public/js/app-main.js` consumes environment data from `app/modules/web/Controllers/Bootstrap/GetEnvironmentController.php`, which returns some fields conditional on session state; compare anonymous, incomplete-authentication and authenticated responses for unintended disclosure. The existing installation, upgrade, status, login, reset and Public Link rows cover the associated user intents, subject to this verification.

### Suggested implementation order

1. Start with existing Use Case seams: Tag, Item Preset, Custom Field, User/Group/Profile, Notification, Plugin, Security, and Public Link management.
2. Add the highest-risk/most central Account flows: edit/delete/create, reveal/change password, history restore, access request, files, favorites, and ACL-denial behavior.
3. Cover login, Master Key unlock, password reset, Public Link viewing/expiry, then user/group/profile administration.
4. Cover configuration and external integrations, import/export and backup, installation/upgrade, then each CLI command.
5. Add interface-specific scenarios only where that interface exists; maintain API/CLI/Web contracts separately and do not assert nonexistent operations.
