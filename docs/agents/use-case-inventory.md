# sysPass use-case inventory for BDD

Status: maintained application use-case catalog. Source survey: 2026-11-16.

## Purpose and scope

This inventory is the maintained source of truth for the application's user-visible intents, their surveyed entry points, implementation evidence, and outstanding decisions. Use the stable IDs to plan BDD scenarios, implementations, and refactors. It covers the vault, access administration, authentication, configuration, installation, maintenance, and other product operations.

The project glossary's **Use Case** means a Domain class with one `execute()` entry point ([`CONTEXT.md`](../../CONTEXT.md), [`ADR-0003`](../adr/0003-use-case-and-command-result-convention.md)). This catalog also includes intents that bypass such a class. Section A retains one row per existing class for traceability, even where classes represent variants of the same intent. Section B records other intents and unresolved workflows. Group related rows into BDD features where appropriate, but preserve their IDs and boundary-specific examples.

This document catalogs what exists and what needs a decision. Explicit **Target** statements record product decisions for future BDD and refactors; they are not claims of current implementation. Other BDD focus cells are scenario prompts, not approved acceptance criteria. Resolve marked uncertainties against an issue, product decision, and applicable ADRs before asserting a desired outcome. Characterization tests may record existing behavior separately without endorsing a defect. The glossary remains authoritative for terminology and ADRs for architectural decisions; discrepancies with the code are explicitly flagged below.

When a change adds, removes, moves, or changes an intent or boundary, update its row, evidence, status, and scenario prompts in the same change. Preserve IDs for unchanged intents; cross-reference IDs when merging or splitting rows. Recheck the source snapshot when updating counts. An inventory entry is not evidence that a scenario has been implemented or passes.

Included: user-visible product behavior across Web/API/CLI, including operational flows. Excluded: static assets, resource delivery, selector/read-model plumbing, generic page composition, navigation-only and rendering-only behavior. The [UI interaction inventory](ui-interaction-inventory.md) owns JavaScript-to-backend wiring detail; it is not a substitute for this application-level inventory.

### Boundary and actor notation

- **W** — Web module; **API** — JSON-RPC API; **CLI** — console command; **Public W** — Web route reachable without normal login. A listed boundary identifies source-observed entry points, not proof that the full workflow succeeds.
- Actor labels, including those in section headings, are candidates for BDD setup, not a finalized authorization matrix: **Anonymous** (not signed in, including a person requesting or completing password recovery), **User** (authenticated sysPass user), **Admin** (application administrator or appropriately authorized profile), **API client** (user acting through an API Token), **Visitor** (Public Link holder), **Operator** (installer/maintainer using Web or CLI), and **System** (automated action). Actor exceptions are stated on individual rows or next to their tables.
- Section A identifies implemented Domain Use Case classes; section B identifies controller/service/other implementations. **Unresolved** identifies incomplete, conflicting, or unverified behavior and is not an implemented acceptance contract. Actual authorization must be verified at each boundary, including denied access.

## Source snapshot

- **63** concrete Domain use cases exist in eight contexts: Account (public-link management only), CustomField, ItemPreset, Notification, Plugin, Security, Tag, and User. Their class locations are under `lib/SP/Domain/<Context>/UseCases/`.
- All 63 are reachable from Web controllers. Ten are reachable from API controllers: Tag's five single-operation methods and User Group's five methods. No current use case is reached from CLI.
- The API currently exposes 29 JSON-RPC methods across Account, Category, Client, Tag, UserGroup, and Config. Account, Category, Client, and Config methods remain service/controller driven.
- CLI has three commands: `sp:install`, `sp:backup`, and `sp:crypt:update-master-password`.
- The source survey found no `*.feature` Gherkin files or prior BDD inventory. Current testing policy is documented in [`testing.md`](testing.md) and [`ADR-0004`](../adr/0004-test-strategy-and-ci-gating.md); browser UI Workflow Tests are limited to JS-to-backend wiring contracts by [`ADR-0012`](../adr/0012-ui-interaction-coverage.md).

These counts describe the surveyed source snapshot, not scenario coverage or product completeness.

### Public Link management — Admin/User; W

Public-link management classes are in `lib/SP/Domain/Account/UseCases/`. Public retrieval by hash is a separate service/controller flow listed in section B.

**Target:** an Account has at most one Public Link at a time; creating one requires current Account access, Public Link creation permission and Account password-view permission. An expired or exhausted link may be replaced by a newly created link under the same creation permissions; retire the old record only when replacement succeeds. Creation and refresh apply configured expiration time and maximum view count. Refresh requires the creator or a separately authorized administrator, current Account access, Public Link management permission and password-view permission; it generates a new URL and current Account snapshot, invalidates the old URL immediately and resets the view counter as one operation. A failed refresh leaves the previous link and view count unchanged. Link editing only changes notifications. The creator or a separately authorized administrator with Public Link management permission may delete a link even without current Account access. Existing links remain valid after access-control changes, including loss of creator access, until explicitly revoked, expired, exhausted or revoked by Account content changes. This intentional public-access behavior requires maintainer security review.

**Snapshot target:** expose Account name, login, password, URL, notes, Client and Category; do not expose custom fields, file attachments, history or access grants. Creating or refreshing a link for a linked child requires Account access and password-view permission for both child and parent.

**Management visibility target:** Only the creator or an authorized application administrator may search for and view a managed Public Link. Enforce the relevant management Action permission and avoid disclosing inaccessible links in search results or direct lookup. This authorization target requires maintainer security review.

**Management boundary evidence:** Web create, refresh and delete controllers check their respective Public Link profile actions. `lib/SP/Domain/Account/Services/PublicLinkAuthorization.php` checks Account visibility and password-view permission for creation and link rebuilding. Creator-or-administrator checks for refresh and deletion are not explicit in the inspected use-case and service methods; verify repository and dispatched paths against the target, including after Account access is lost. These source checks do not establish complete authorization.

**Creation response and snapshot source:** Both Web creation submissions inherit completed-login checking, check the create Action and return caught exception messages as Action errors. Their use cases check Account visibility and password-view permission before creation; the service checks again while building the snapshot, derives expiration and view limit from configuration, and reads the session Master Key for snapshot encryption (`app/modules/web/Controllers/PublicLink/SaveCreateController.php`; `SaveCreateFromAccountController.php`; `lib/SP/Domain/Account/Services/PublicLink.php`). The use cases emit their creation event after the service call, while the controllers return a generic success message rather than the generated URL. Test denied permissions, inaccessible Accounts, unavailable Master Key and generated-link retrieval through dispatch and persistence, including absence of partial links and sensitive error content; source order does not establish those outcomes.

**Refresh and deletion result source:** The Web refresh and delete Actions inherit completed-login checking, check their respective Actions and map caught exception messages to errors. Refresh looks up the link, rebuilds its snapshot and returns the repository's affected-row boolean; the use case does not inspect that boolean before emitting its event. The single-delete repository returns no affected-row result to the service; batch deletion compares affected count after deletion (`lib/SP/Domain/Account/UseCases/RefreshPublicLinkUseCase.php`; `lib/SP/Domain/Account/Services/PublicLink.php`; `lib/SP/Infrastructure/Account/Repositories/PublicLink.php`). Test missing, concurrently removed and unauthorized links, failed persistence and event outcomes through dispatch and read-back. These observations do not establish an effective response or mutation.

### Notification — Admin manages; User receives/marks; W

Classes are in `lib/SP/Domain/Notification/UseCases/`. **Target:** Users may view and mark notifications addressed to them or explicitly broadcast to all Users; a broadcast is retained until an authorized administrator removes it, including for Users created after it was issued. Non-sticky visibility is subject to its visibility period and each recipient's dismissal state; sticky visibility follows the start and removal rules below. Cross-user viewing or marking, and access to admin-only notifications, require an appropriate explicit administrative permission, not merely a generic administrative role. Read state for a broadcast is per recipient; an administrator marking it for a recipient changes only that recipient's state. A sticky notification stays visible to its intended audience until an authorized administrator removes it, regardless of individual read state; sticky status does not override recipient or admin-only restrictions. The current model stores one `checked` flag, so per-recipient state is not established by that model. Confirm actor scoping at the driving adapter; a successful ID-based use case call alone does not establish that a User may access that notification.

**Notification validation and delivery targets:** Creation and editing require nonblank content after trimming and reject invalid time ranges before saving; validation failure leaves the existing notification unchanged. A successfully saved in-app notification remains available if optional email or push delivery fails; record the delivery failure separately without secrets. External delivery behavior and event ordering require source and implementation verification.

**Further notification targets:** A recipient may dismiss a non-sticky notification for themselves only; dismissal does not delete the notification or affect other recipients, including future broadcast recipients. Sticky notifications remain visible until an authorized administrator removes them. If a recipient loses eligibility and later regains it, preserve their previous read and dismissal state while denying visibility during ineligibility. Send optional email or push once at the notification's start time, or on creation if already active, to recipients eligible at delivery time; do not retry automatically. Future recipients of a broadcast see it in-app but receive no historical external delivery. Editing an undelivered notification updates its pending schedule, content and eligible audience; editing after delivery never schedules another send. Creation requires a recognized component and type; editing follows the legacy-value exception below. Both require an explicit valid audience: targeted, broadcast or admin-only. Sticky is independently selectable, subject to the existing explicit permissions and audience restrictions. Limit component and type to 100 characters each and content to 5,000 characters; reject over-limit input without truncation and preserve readability of existing notices. The current model has no schedule bounds and one shared checked flag; per-recipient dismissal and delivery scheduling are not established (`lib/SP/Domain/Notification/Models/Notification.php`; `lib/SP/Infrastructure/Notification/Repositories/Notification.php`).

**Taxonomy and channel targets:** Maintain a registry of stable, nonlocalized component and type identifiers with separately translated labels; registered Plugins may contribute identifiers. Preserve historical free-text values as readable legacy values without guessing their identity. On editing an existing notice, an administrator may preserve unrecognized legacy values unchanged, but changing either field requires a recognized identifier for that field. If a contributing Plugin is disabled, deleted or unavailable, existing notices retain its identifiers and last-known display labels; new notices cannot select those identifiers until the Plugin is registered and available again. An authorized notice creator explicitly selects no external channel, email, push or both. Deliver only through configured, available selected channels to eligible recipients with a usable email address or registered device; configured event mail must not duplicate the same notice delivery. If a selected channel is unavailable or an eligible recipient lacks the required address or device at delivery time, preserve the in-app notice and record a secret-free per-channel or per-recipient skipped or failed outcome without automatic retry. If the first delivery opportunity occurs after a non-sticky notification expires, skip the external send and record it as missed. If the scheduler resumes while a due notice remains active, attempt the pending send once at the next opportunity using current eligibility, without automatic retry. **Current gaps:** Web fields accept free text, and automatic Account notices can store translated labels (`app/modules/web/Forms/NotificationForm.php`; `lib/SP/Domain/Notification/Services/NotificationEvent.php`). Mail uses event subscriptions rather than a demonstrated per-notice channel selector (`lib/SP/Domain/Notification/Services/MailEvent.php`); push and scheduling are not established by the inspected paths. Historical values and Plugin extensions require persisted-data compatibility review.

**Registry and delivery concurrency targets:** Initially cover the observed Account request and Public Link view notification producers; add core identifiers as further producers are inventoried rather than assuming a complete set now. Prevent duplicate external send attempts when schedulers race or restart. An interrupted send with an uncertain outcome may be recorded as unknown and must not be automatically retried, even if that means delivery cannot be confirmed.

**Sticky start target:** A future-dated sticky notification becomes visible at its start time and remains visible until an authorized administrator removes it, regardless of its end time or individual read state. Audience and administrative access restrictions continue to apply.

**Notification Web boundary evidence:** The view, search and check controllers check their respective profile Actions. The inspected ID-based view lookup has no explicit recipient predicate. `app/modules/web/Controllers/Notification/DeleteController.php` inherits a completed-login check and passes the application-administrator flag to its use cases, but its action has no explicit delete-Action check; the inspected single-delete repository methods distinguish sticky and administrator cases without a recipient predicate. Verify direct cross-user and unauthorized requests, downstream checks and safe responses against the audience and dismissal targets above; runtime behavior remains unverified.

The use case calls the service and emits its event after that call; `Notification/Services/Notification.php` throws a not-found exception on zero affected rows, and `Infrastructure/Notification/Repositories/Notification.php` updates the shared `checked` column with an ID predicate. The inspected path does not pass a recipient to that update. The service chooses an administrator or non-administrator query using the current User. ### Security — Admin; W

Classes are in `lib/SP/Domain/Security/UseCases/`.

**Security retention and clear targets:** Retain ordinary event-log entries and Tracks until explicitly cleared; retain event-log-clear audit records indefinitely outside the ordinary clear set. Users with explicit security-audit permission may view and export these secret-free records, including actor, time and available client address; deny unauthorized access. Clearing an already-empty event log or Tracks collection succeeds as an audited no-op, subject to the same required audit persistence and failure rules. Clearing Tracks resets all active abuse controls represented by them; unlocking resets the affected Track's controls only. Current event-log and Track repositories return false for a clear affecting no rows; verify adapter behavior rather than treating that result as the target (`lib/SP/Infrastructure/Security/Repositories/Eventlog.php`; `lib/SP/Infrastructure/Security/Repositories/Track.php`). Security and retention changes require maintainer review.

**Abuse-control target:** Count failed login and API credential authentication attempts separately by client address and source in a rolling ten-minute window, including unknown or disabled Users and invalid API Tokens. Exclude authorization denials after successful authentication and requests rejected while already locked; successful attempts do not consume the failure budget. After ten failures reject further attempts for that address and source until the window expires or an authorized administrator unlocks or clears the relevant Track. This intentionally affects Users sharing an address. If tracking storage is unavailable, fail closed with a safe temporary-unavailable response and record a secret-free operator diagnostic when possible. The current Track service and repository require runtime verification: the repository query uses `LIMIT 1` while the service compares the returned row count to a threshold (`lib/SP/Domain/Security/Services/Track.php`; `lib/SP/Infrastructure/Security/Repositories/Track.php`). These authentication and abuse-control targets require maintainer security review.

**Authentication tracking source:** Web login adds tracking for blank credentials before checking the existing tracking state; the shared login check also adds a Track when its threshold is reached (`lib/SP/Domain/Auth/Services/Login.php`; `LoginBase.php`). API setup checks tracking first and adds a Track on the threshold path and in its access-denied helper, whereas its caught missing-token lookup returns a generic error without an explicit tracking call in that catch (`lib/SP/Domain/Api/Services/Api.php`). The Track service builds the bucket from source and client address and delays when its threshold is reached (`lib/SP/Domain/Security/Services/Track.php`). Exercise failed credentials, already-limited requests, authorization denial and tracking-store failure through Web and JSON-RPC, with independent Track reads; source paths do not establish effective counts or timing.

**Track identity target:** A managed Track represents one client-address-and-source abuse-control bucket. Unlocking it resets the entire bucket's failure budget without affecting other buckets. Current persistence stores individual attempt rows and unlocks one row, not an established aggregate bucket (`lib/SP/Infrastructure/Security/Repositories/Track.php`). Migration and retention of existing Track data require compatibility review.

### Account vault, access, history, credentials, and files

Core Account create/edit/delete/search/view APIs and Web controllers remain service-driven; `lib/SP/Domain/Account/UseCases/` currently contains only Public Link use cases.

**Account authorization target:** Every Web and API operation on an Account requires both the relevant User Profile action permission and the appropriate Account-level access. Account edit, password change, and deletion require edit access, not visibility alone. A private Account is accessible only to its owner, including against administrators and other explicit or group grants. A group-private Account is accessible only to Users whose primary group is the Account's main group, without administrator or secondary-membership override; if both privacy flags apply, both restrictions must hold. Subject to privacy and profile permissions, the owner and main-group members retain edit access ahead of conflicting direct read-only grants. Otherwise an explicit User grant takes precedence over secondary-group grants; if there is no direct User grant, any matching secondary-group edit grant permits editing. Retain the full-group-access configuration for evaluating secondary memberships in explicitly shared secondary groups; membership in the Account's main group remains recognized, subject to privacy. Global search requires both global configuration and profile permission and may reveal only name, Client and Category for otherwise inaccessible non-private Accounts, without login, URL, notes, custom fields, password, file names or history; discovery does not confer Account access. Enforce these rules server-side, including alternate entry points; current page, search, and mutation paths do not consistently use the same resource checks. These targets require maintainer security review before behavior changes merge.

**Visibility filter source:** `AccountReader::isVisible` delegates to the Account repository, which applies `AccountFilter::buildFilter()` with its default non-global-search argument and tests for a matching ID (`lib/SP/Domain/Account/Services/AccountReader.php`; `lib/SP/Infrastructure/Account/Repositories/Account.php`). The builder applies owner, group and sharing predicates for non-administrators, with an additional secondary-group sharing branch when configured; it applies private and group-private predicates separately after that administrator branch. Its history filter uses fields from the history row (`lib/SP/Domain/Account/Services/Builders/AccountFilter.php`). Verify actual visibility and denied mutations across actor, privacy and grant combinations, and compare history against current Account access. These query-building observations do not establish edit authority or dispatched outcomes.

**Account password boundary source:** API password view calls API setup before fetching the password record; the repository fetch uses the Account visibility filter. The Web password helper checks the password-view Action and Master Password update state before decryption. Web password submission checks its Action and visibility; API password submission checks its Action through setup and delegates to the writer (`app/modules/api/Controllers/Account/ViewPassController.php`; `EditPassController.php`; `app/modules/web/Controllers/Account/ViewPassController.php`; `SaveEditPassController.php`; `app/modules/web/Presenters/Helpers/Account/AccountPasswordHelper.php`; `lib/SP/Infrastructure/Account/Repositories/Account.php`). Verify denied, read-only and linked-parent cases through both boundaries, including secret-free errors, counters and unchanged persistence. These source checks do not establish the complete linked-credential or edit-access targets.

**API Account mutation evidence:** `app/modules/api/Controllers/Account/EditController.php` and `DeleteController.php` call API setup for their respective profile actions. The inspected writer paths in `lib/SP/Domain/Account/Services/AccountWriter.php` check Account visibility, which alone does not establish the edit-access target. Verify read-only, private and cross-group denial through JSON-RPC and independent persistence checks; review data fetched before denial for unintended response disclosure.

**Account create and update target:** Web and API both require an Account name, an existing Client and Category, and a password unless an accessible parent Account supplies it. A linked Account may point only to an existing, accessible non-linked parent; reject self-links, chains and cycles. When a creator lacks permission-management authority, use that User as owner and their primary group as the Account's main group, ignoring attempted ownership or sharing overrides. Across Web and API updates, omitted optional fields and ACL collections remain unchanged; an explicitly supplied empty collection clears it. Fixed Item Presets still apply to controlled fields even when omitted, and win over conflicting explicit values or empty collections; the response reflects the effective saved value. Only the owner may set or clear privacy flags. Ownership transfer and User/group grant changes require permission-management authority and may be performed by the owner or a separately authorized Account administrator who already has Account access; edit access alone is insufficient to change grants. A User whose primary group is the current main group and who has permission-management authority and Account access may also change the Account's main group. On private Account ownership transfer, the former owner immediately loses access and the new owner gains access subject to their profile permissions. Reject transfer of an Account that is both private and group-private to a User whose primary group differs from the Account's main group unless the group-private restriction is also resolved. Additional field-specific validation remains to be decided. Current collection and adapter semantics differ, so do not assume the target is implemented.

**Linked credential target:** A User linking a child requires access and password-view permission for the parent. Revealing an inherited child password requires Account access and password-view permission for both the child and parent. Changing the child's parent requires access and password-view permission for both the current and new parents. Unlinking requires Account edit and password-change permission on the child and access and password-view permission for the current parent. Linking, unlinking or changing the parent atomically revokes the child's Public Link. A parent password change automatically changes its children's effective password and atomically revokes affected children's Public Links. If the parent is missing or inaccessible, password reveal and Public Link creation/refresh fail closed without a password fallback. An already issued child Public Link remains usable after its creator loses parent access alone, subject to the Public Link lifecycle above. Account names are trimmed and must contain at least one non-whitespace character on Web and API.

**Account validation and update atomicity target:** Duplicate trimmed Account names are permitted, including within the same Client and Category. An explicitly blank optional text field clears it; omission preserves it. Account passwords follow the configured Account password Item Preset or policy. Account creation, initial custom fields, grants and fixed preset effects are all-or-nothing on Web and API. For each updated Account, the update, history snapshot, custom-field changes and any required Public Link revocation succeed or fail together without partial state. An update with no effective change after presets succeeds without creating history or revoking a Public Link. Bulk edits apply the same single-Account rules but allow partial success; report individual failures. The current bulk writer uses a transaction, so do not assume partial success is implemented.

**Account field-length target:** Web and API enforce maximum lengths of 100 characters for name, 50 for login, 255 for URL/IP and 5,000 for notes, rejecting over-limit input rather than truncating it. URL/IP is optional text, not restricted to URL or IP syntax. Existing stored values remain readable and are not silently truncated during unrelated updates. These limits appear in the Web form; equivalent server-side enforcement across boundaries is not established.

**Account file target:** Each operation requires its profile action and Account access: view access for list, search, preview and download, and edit access for upload and deletion. Application-layer encryption of file contents and thumbnails is not required by this target. Batch deletion deduplicates IDs and deletes all or none if a file is missing or unauthorized, without disclosing inaccessible file details. **Current gap:** the upload path uses 1,000 bytes per configured unit, accepts either declared or detected MIME and stores file bytes without application-layer encryption; end-to-end authorization is not established by the controller alone.

**Account history access and deletion target:** History operations require the relevant history action and applicable Account access and privacy restrictions. **Account deletion and restoration target:** Single and bulk deletion create a recoverable deletion snapshot containing encrypted core fields and custom-field values for each Account. Persisted-data and ciphertext changes require compatibility review under ADR-0005.

### Configuration, import/export, backup, and cryptographic administration

The Web configuration controllers use `ConfigFileService`, configuration services, and domain services directly. These operations are security-sensitive; follow [`security.md`](security.md) and obtain maintainer security review before turning them into behavior changes.

**Configuration targets:** Reject invalid submitted values rather than silently discarding them; preserve omitted or masked secrets. A failed save leaves the previous effective configuration intact, and a success audit follows persistence and required side effects. LDAP and mail checks use submitted settings without saving them and report actionable, secret-free failures, including timeouts. **Current gaps:** configuration XML is saved before its cache and subsequent callbacks; invalid mail recipients and event names can be discarded (`lib/SP/Domain/Config/Services/ConfigFile.php`; `lib/SP/Domain/Config/Dtos/ConfigInput.php`). Full rollback and boundary security require verification.

**Import targets:** Support seven-field CSV (Account name, Client, Category, URL, login, password, notes), KeePass XML and sysPass XML; do not claim support for binary KeePass or other MIME types merely listed in the code. Reject malformed files, failed integrity checks and invalid required decryption credentials before any changes. Otherwise allow independent per-record partial success with safe results and atomic creation per record. LDAP import creates missing Users and optionally Groups, skips existing identities without overwriting them, and reports safe per-item outcomes while continuing independent items, subject to the existing delegation ceiling. **Current gaps:** file importers catch some per-record errors within an enclosing transaction; sysPass XML integrity failure is logged but does not abort. The LDAP import path creates Users and Groups but does not establish membership mapping or comprehensive result reporting (`lib/SP/Domain/Import/Services/ImportStrategy.php`; `lib/SP/Domain/Import/Services/SyspassImport.php`; `lib/SP/Domain/Import/Services/LdapImport.php`). Import formats, authorization and persisted-data compatibility require review.

**Backup, export and recovery targets:** Full system recovery remains an operator-managed procedure, not an in-app restore; document required database, application files, configuration and keys, and version compatibility. Preserve previous usable backup and export artifacts until replacements are successfully generated and verified; clean up failed new artifacts where possible and emit no success event on failure. XML export is a privileged system-wide operation, including Accounts outside the actor's ordinary Account ACL, requiring explicit export permission and a nonempty export password. Treat backups and configuration artifacts as sensitive and access-controlled even when not encrypted by the application. **Current gaps:** the backup and export paths remove prior artifacts before completion; Web and API XML exports differ in verification and archiving, and the API returns a server path. No production whole-system restore action was established (`lib/SP/Domain/Export/Services/BackupFile.php`; `lib/SP/Domain/Export/Services/XmlExport.php`; `app/modules/api/Controllers/Config/ExportController.php`). **Master Password targets:** A change succeeds only when every required Account, history and Custom Field update and associated metadata are consistent; failure must preserve recoverability and must not silently accept skipped records. **Import refinements:** Each valid imported Account creates a new Account even if its name matches an existing one; reuse matching Client, Category and Tag definitions and never overwrite existing Accounts. ### Gaps to resolve during BDD refinement

1. **Account is the largest service-driven area.** Account create/edit/delete/view/search, password operations, history, files, favorites, access requests, and bulk management are not represented by Account Domain Use Cases. The Account UseCases directory covers Public Links only.
2. **Category and Client are service/controller-driven.** Their CRUD/search APIs are not use-case-backed.
3. **Authentication and session lifecycle are service/controller-driven.** Make local, LDAP and browser/Basic login, Master Key unlock, failed login, session expiry, and logout explicit scenarios. Password-reset request and completion are public Web flows, not authenticated-only actions.
4. **Configuration, installation, upgrade, import/export, backup, and cryptographic administration are service/controller/CLI flows.** Their validation and side-effects are split across layers.
5. **API parity is incomplete.** API covers 29 methods in six areas; it does not expose all Web behavior. Do not imply parity by copying Web scenarios wholesale.
6. **Authorization often sits outside the Domain Use Case.** A Use Case unit scenario cannot by itself prove Web/API authorization; assert denial at the relevant adapter boundary.
7. **Public-link management and public-link viewing are different intents.** `GetPublicLinkUseCase` is ID-based management; anonymous retrieval by hash, expiry, max-view enforcement, and serialized payload behavior are in `ViewLinkController`/`PublicLinkService`.
8. **Some outcomes are undefined or source-level defects.** The UI interaction inventory records route/outcome discrepancies, including handlers that continue after error envelopes; its `status/checkRelease` missing-route observation is stale against the current controller and dispatch source. Public Link editing has a target contract but no save route. DokuWiki API configuration/testing and embedded DokuWiki viewing are retired; their missing routes are not implementation requirements.
9. **No dedicated reporting subsystem was found.** Event log, Tracks, and Account history are the product's nearest audit/history surfaces; do not invent separate report use cases without new evidence.
10. **Security-sensitive behavior requires maintainer review.** The decided authentication, Public Link and notification authorization targets, along with other changes to authorization, cryptography, Master Password and credential export/import, need explicit maintainer security review before behavior changes merge; see [`security.md`](security.md). A target decision is not itself that review.
11. **Category deletion target requires verification.** Categories are flat; Account or Account history references block deletion, and a batch with a blocked, missing, or unauthorized Category is rejected in full. Preserve historical information unless an authorized user explicitly deletes the history. Verify current behavior and cover both boundaries without assuming the batch implementation is atomic.
12. **Password-reset behavior differs from the target and ADR-0003.** `RequestPasswordResetUseCase` emits the request event before sending mail; `ResetPasswordUseCase` marks the token used before the password update. The targets specify success-event timing, separate failure recording, a generic response, token invalidation on a new request and retryable atomic completion. Verify transaction and failure behavior rather than assuming it. The failure-recording mechanism must respect ADR-0003 and avoid exposing secrets.
13. **Identity deletion and delegation need implementation.** The targets above decide ownership and membership blockers, historical identities, self-deletion, last-administrator protection, partial-success batches, delegation limits, installer defaults and deleted-Account reference recovery. Current schema constraints and services do not establish those targets. Security and persisted-data compatibility review remain required.
14. **Credential lifecycle policies need implementation.** Targets now require 90-day default per-token expiry with a finite maximum, scoped rotation and redaction; password-change/reset session and token invalidation; immediate disablement effects; and fresh authentication before Master Key reload. Verify them against API/session paths and retain security review. Provider registration order and configuration-dependent authority still require implementation characterization against the approved no-fallback rule.
15. **Operational detail remains unresolved.** Configuration field-specific bounds and wiki filter semantics; import XML versions and remaining collision handling; exact backup completeness checks, recovery instructions and upgrade supported versions; and installation/reinstallation safeguards require further decisions or source verification. Temporary credential delivery eligibility, secure one-time presentation and the mechanisms for atomic rotation, artifact authorization and key recovery need implementation design and security review. The approved targets above do not establish current behavior or complete cross-boundary coverage.
16. **Identity authorization needs characterization.** Deleted-identity recovery authorization and the horizon for future delegated access need precise implementation characterization without weakening the approved fail-closed and delegation rules.
17. **Public and partially initialized routes need a boundary audit.** `app/modules/web/Init.php` lists installation, upgrade, status, bootstrap environment, resource and error controllers for partial initialization; those controllers skip the full initialization branch, including its CSRF check. This list alone does not establish anonymous access or successful runtime reachability. The two legacy status paths' inspected dispatch and controller code have no explicit authentication or ACL gate, unlike `status/checkRelease`; runtime and external proxy restrictions remain unverified. Verify the other routes and denied requests before assigning actors. Resource and error presentation and bootstrap environment are supporting behavior rather than separate intents under this inventory's scope. `public/js/app-main.js` consumes `bootstrap/getEnvironment` from `app/modules/web/Controllers/Bootstrap/GetEnvironmentController.php`: its action does not call the login check, and returns configuration, enabled Plugins, public key and session-related values; update and notice flags depend on completed authentication and admin or demo status, while notification preference depends on logged-in status. Compare anonymous, incomplete-authentication and authenticated responses for unintended disclosure and verify effective runtime access. The existing installation, upgrade, status, login, reset and Public Link rows cover the associated user intents, subject to this verification.

   **Environment and Web error source:** The environment action obtains enabled Plugins through the Plugin manager, returning an empty list when that lookup throws; the repository selects enabled Plugin models (`lib/SP/Domain/Plugin/Services/PluginManager.php`; `lib/SP/Infrastructure/Plugin/Repositories/Plugin.php`). Public-key lookup falls back from session to the PKI handler and returns an empty string on a caught file error. The action reads the session CSRF value, while the JavaScript requests this environment during bootstrap. Check responses and diagnostics for sensitive values under anonymous, incomplete and completed sessions, including debug mode and failed dependencies. Separately, `app/modules/web/Bootstrap.php` maps specified authorization exceptions to a forbidden response, catches session timeout separately, and constructs an internal-error response with exception trace data for other caught exceptions. Verify each rendered or JSON response and diagnostic sink through dispatch; source construction alone does not establish the emitted payload.

   **Resource route source:** Both CSS and JavaScript controllers inherit `ResourceBase`, whose constructor verifies a request signature before the Action (`app/modules/web/Controllers/Resource/`; `lib/SP/Domain/Http/Services/Request.php`). `LayoutHelper` constructs signed resource links. The Actions select default bundles or build requested file handlers, then defer minification to a response callback; the requested base goes through the application-path resolver. Test generated links, missing or altered signatures, invalid paths, missing files and callback failures through dispatch, including safe error responses and absence of unrelated file contents. The partial-initialization listing and source checks do not establish effective reachability or emitted content.

   **Database error route source:** Full Web initialization checks installation and database connection before maintenance and table checks, redirecting to separate database-connection and database-error routes on the corresponding failures. Both error controllers are in the partial-initialization list and render public-layout messages; context initialization, language setup and HTTPS checking occur before the partial-initialization branch (`app/modules/web/Init.php`; `app/modules/web/Controllers/Error/DatabaseConnectionController.php`; `DatabaseErrorController.php`). Test direct and redirected requests with connection and table failures, including initialization and rendering dependency failures, status, redirect chains and secret-free responses. Controller source alone does not establish that the error page is reachable when its dependencies fail.
18. **Maintenance error dispatch needs characterization.** `app/modules/web/Init.php` redirects requests during maintenance to `error/maintenanceError`, but `app/modules/web/Controllers/Error/MaintenanceErrorController.php` is absent from the partial-initialization list. The source therefore warrants a dispatched test for repeated redirects and a usable maintenance response, including the lock-holder AJAX exception in `lib/SP/Core/HttpModuleBase.php`. Existing controller-level error tests do not establish the outcome through dispatch.

   The inspected maintenance check permits its exception only for an AJAX request with a positive lock matching the logged-in User ID; other requests are directed to the maintenance route. The maintenance Action itself uses a public layout and returns rendered warning content (`app/modules/web/Controllers/Error/MaintenanceErrorController.php`), but it is reached only after initialization. Test both the redirect chain and the lock-holder conditions through dispatch, including incomplete authentication; do not infer reachability from the Action alone.

### Suggested implementation order

1. Start with existing Use Case seams: Tag, Item Preset, Custom Field, User/Group/Profile, Notification, Plugin, Security, and Public Link management.
2. Add the highest-risk/most central Account flows: edit/delete/create, reveal/change password, history restore, access request, files, favorites, and ACL-denial behavior.
3. Cover login, Master Key unlock, password reset, Public Link viewing/expiry, then user/group/profile administration.
4. Cover configuration and external integrations, import/export and backup, installation/upgrade, then each CLI command.
5. Add interface-specific scenarios only where that interface exists; maintain API/CLI/Web contracts separately and do not assert nonexistent operations.
