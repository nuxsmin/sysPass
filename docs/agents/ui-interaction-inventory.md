## Purpose and scope

This is the authoritative inventory of JavaScript-to-backend wiring contracts in the Web interface. For every user-initiated, JavaScript-bound control it records:

- the stable trigger and the delegated JavaScript handler;
- the Action route, HTTP method and payload shape actually dispatched;
- the documented success and error outcome, including whether an independent read is required;
- the ACL action and profile context that exposes the control;
- the committed test evidence and the coverage status.

The inventory is a living review artifact for [ADR-0012](../adr/0012-ui-interaction-coverage.md). It is scoped to wiring only. It does not replace [Testing](testing.md), [UI Smoke Suite](ui-smoke-suite.md) or [UI Workflow Tests](ui-workflow-tests.md).

### Non-goals

- Layout, composition, visibility-only conditions, usability, viewport/mobile behaviour and pixel/visual checks.
- Authorization and denied-access behaviour. Those are enforced and tested at the HTTP/backend layer; hiding a control is not proof of server-side authorization.
- Page-load rendering contracts owned by Tier A and Tier B. The inventory cites them only where they provide partial wiring evidence.
- Migration of legacy bindings to the binder described by issue #2126.
- Changes to the discovery mechanism, production code, tests, fixtures or workflows.

## Discovery method

The inventory is the union of four static enumerations, cross-checked against a browser snapshot:

1. **Template bindings** under `app/modules/web/themes/material-blue/views`: `data-route`, `data-view`, `data-onclick`, `data-onsubmit`, `data-action-route`, `data-action-next`, `data-action-form`, `data-action-route-on`, `data-action-route-off` and `data-onchange`.
2. **Delegated handlers** in `public/js/app-triggers.js` (`bodyHooks`, `views.*`), `public/js/app-actions.js`, `public/js/app-main.js` (clipboard) and `app/modules/web/themes/material-blue/js/app-theme.js` (search and favorites).
3. **Grid and action builders** in `app/modules/web/Presenters/Helpers/Grid/*.php`, `app/modules/web/Presenters/Helpers/Account/AccountActionsHelper.php` and `app/modules/web/Presenters/Helpers/LayoutHelper.php`.
4. **Controller Actions**: 184 controller classes contain 186 `*Action` methods, of which 14 are `getAclAction`; 172 are route actions. Routes resolve as `SP\Modules\Web\Controllers\<Controller>\<Action>Controller` (`app/modules/web/Bootstrap.php:84-89`). A dispatched route with no matching controller is recorded as Undefined or Blocked, never Covered.

Each dispatched route was checked against its controller file and method. Expected success and error outcomes were taken from the controller's `ActionResponse`, the handler's status handling, or a committed test. Where no outcome is documented, the row says `UNDEFINED` and links a discrepancy.

## Status legend

| Status | Meaning |
| --- | --- |
| **Covered** | A committed wiring test (WIRING or WRITE) exercises the control's dispatch and documented success outcome. It does not imply error coverage. |
| **Partial** | Committed evidence exists, but only a page load, a Tier A/B navigation, or a success-only render. It is not the full wiring contract. |
| **Untested** | No committed test exercises this interaction. |
| **Undefined** | The route, controller or expected outcome cannot be documented from sources. The row links a discrepancy; current behaviour is not blessed. |
| **Blocked** | The interaction exists but cannot be exercised in the current fixture or configuration. |
| **Excluded** | Out of scope per ADR-0012 pending a maintainer decision and security review. Listed for completeness only. |

## How to read the tables

- `JS handler` is a source reference in `file:line` form. Controller references use the same form.
- Handler names without a file prefix (`account.save`, `appMgmt.delete`, `grid.search`, `plugin.toggle`, `notification.check`) are defined in `public/js/app-actions.js`. Theme handlers named `app-theme.js` are in `app/modules/web/themes/material-blue/js/app-theme.js`. A bare line range such as `423-446` continues the handler file named immediately before it in the same cell.
- The wire envelope is the `ActionResponse` JSON (`lib/SP/Domain/Common/Dtos/ActionResponse.php:98-104`): `status` is the string `OK`, `ERROR` or `WARNING`. `public/js/app-requests.js:156-163` maps it to numeric `0`, `1` or `2` before handlers; `public/js/app-main.js:347-385` renders it.
- `200 + OK` means HTTP 200 plus wire status `OK`. `OK + itemId/nextAction` means the JSON `data` contains those fields.
- Each table inherits `Last verified: 2026-11-12`. If a row is re-verified separately, append the date in its Notes cell.
- `UNDEFINED` is deliberate. It means the source does not document an expected outcome; it is not a placeholder for a guessed one.

## Review process

**Ownership**

- The UI workflow owner owns structure, status values, stable IDs and test links.
- Feature reviewers own backend outcomes, controller envelopes and persistence claims for their area.
- A maintainer owns security-sensitive or Excluded rows, including credentials, public links, export, encryption, backup and configuration.

**Pull-request checklist**

- Update the inventory when adding or altering any `data-*` binding, delegated handler, grid action, Action route or controller `*Action`.
- Add or update a committed test, or mark the row Undefined/Untested with a linked follow-up issue. Do not mark an outcome Covered without evidence.
- Writes need an independent authorized read that proves persistence, not only a visible success message.
- Credential, public-link, export, encryption, backup and configuration surfaces need a maintainer decision or an explicit Excluded status.
- Keep `Last verified` current. Each table carries a `Last verified` field; append a row-level date in Notes when a row is re-verified separately.

**Stable IDs**

IDs are stable and never renumbered. Use `UI-<AREA>-<ACTION>` with uppercase segments. If an interaction is retired, keep the row and mark it Excluded with a note; do not reuse the ID for a different interaction. Grouped rows may name several routes, but the ID names the family.

**No new CI gate**

This inventory is a review artifact, not a CI gate. It does not add a required check and does not change branch protection. Gaps become follow-up issues using the existing labels (`needs-triage`, `ready-for-agent`, `ready-for-human`, `wontfix`) described in [Triage labels](triage-labels.md).
